Accessibility

Most accessibility comes free when you use the right HTML element. ARIA is the patch for when you can't. The order of effort is: semantic HTML → keyboard support → focus management → ARIA, and only then carefully.

Start with semantics

A <button> is focusable, keyboard-activatable, and announced as a button — for free. A clickable <div> is none of those. Same pixels, very different experience.

Live example — try Tab. Only the first is reachable

A <div> — not tabbable
  • Use landmarks: header, nav, main, footer — screen readers navigate by them.
  • One h1; headings in order describe the page's outline.
  • Every input has a label; every image has meaningful alt (or alt="" if decorative).

Keyboard & focus

Everything clickable must be reachable and operable by keyboard. That means a visible focus style — and never removing it without a replacement. Focus is how keyboard users know where they are. 

/* Tailwind: a ring that appears only for keyboard focus */
focus-visible:ring-2 focus-visible:ring-brand-500 focus-visible:ring-offset-2 focus-visible:outline-none

Focus management is the advanced part: when you open a dialog, move focus into it and return it to the trigger on close; when a single-page app swaps the view, move focus somewhere sensible. The app's switchView() focuses #view; its palette traps focus and restores it.

ARIA — the patch, not the plan

ARIA attributes tell assistive tech things the HTML alone doesn't say. There are two kinds — roles ("this is a menu") and states ("it is currently expanded"). States change as the UI changes, so JS must keep them in sync.

AttributeSays
aria-expandeda disclosure is open/closed
aria-presseda toggle is on/off
aria-current="page"this nav link is the active page
aria-describedbyextra description (error text, tooltip)
aria-live="polite"announce this region when it changes
aria-labela name for an icon-only control

Two rules of thumb: no ARIA is better than bad ARIA, and the first rule of ARIA is "don't use ARIA if a native element does it". The app's Overlays & Pickers view is a tour of doing this correctly — menu, popover, and combobox each keep their states honest.

Live example — an announcement

Screen readers can't see a toast appear. A live region is where you put text for them to read aloud. Press the button: 

<p role="status"></p>

status.textContent = 'Saved'   // announced without stealing focus

How to test it

  • Unplug the mouse. Can you do everything with Tab, Enter, Space, Escape, and arrows? Can you always see where focus is?
  • Zoom to 200%. Does the layout survive? Is text still readable?
  • Run axe DevTools (free browser extension) for automated catches like missing labels and contrast.
  • Use a screen reader once. VoiceOver (built into macOS) or NVDA (free on Windows). Ten minutes is worth a hundred `aria-` guess.

The app also honors prefers-reduced-motion with one global rule, and ships a "Skip to content" link — press Tab as soon as the app loads and you'll meet it.

Exercise

  1. Take any page you built and do the whole tab pass without a mouse. Fix anything you can't reach.
  2. Add an icon-only button and give it an aria-label.
  3. Add a toggle that keeps aria-pressed in sync with its state.
  4. Run axe DevTools on the pattern library and fix one finding.
